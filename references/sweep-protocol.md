# 遍历与账本协议

> 覆盖率不是感觉，是行数。账本有四张表，每张表的行数就是你的分母。

## 顺序：为什么不能从测试读起

```
题面契约（R 表 + 预期断言，先落盘）
  → 环境基线
  → 测试静态遍历（账本 A）
  → 流程账本（账本 F：test.sh / test.py）
  → 变异探针
  → rubric 三仿真（账本 C）
  → 三向追溯（账本 B）
  → 归并成稿
```

先读题面的目的不是「知道答案」，是**先写下你预期的断言**。带着预期读测试，才会发现「它没测我以为它测的东西」。反过来，先读测试会被它的措辞锚定，把「它写了什么」当成「题面要求什么」。

## 账本 A：测试函数

文件：`work/ledger-tests.md`

| # | 文件 | 函数 | 行号 | 声称验证 | 实际断言 | 结论 | 依据 | issue |
|---|---|---|---|---|---|---|---|---|
| 1 | tests/test_outputs.py | test_cancel_pending | 12–20 | 取消未开始任务 | 只查 `error == "CancelledError"` | 可疑 | L16；未查 steps | T01 |
| 2 | tests/test_outputs.py | test_cleanup | 44–58 | finally 执行 | 只查 `elapsed < 0.5` | 已确认 | L52；未查 cleanup 标志 | T04/T05 |
| 3 | tests/test_outputs.py | test_isolation | 60–70 | 取消互不影响 | 只查 A 状态 | 已确认 | L66；未查 b_steps | T03 |

规则：
- 一个函数一行；函数里有多个独立断言组（如先测 pending 再测 done），拆子行（`3a`、`3b`）。
- 「结论」只能是 OK / 可疑 / 已确认。**不允许空。**
- 「实际断言」写断言真正能区分的两种行为，不抄函数名。
- 「依据」写行号或变异体编号，不写「见上文」。

## 账本 F：流程（test.sh / test.py）

文件：`work/ledger-flow.md`

| # | 文件:行 | 这一行做什么 | 失败时会怎样 | 结论 |
|---|---|---|---|---|
| F1 | tests/test.sh:4 | `pytest ... \|\| true` | 退出码恒 0 | 已确认：吞失败 |
| F2 | tests/test.sh:5 | `echo 1 > reward.txt` | 无条件 reward 1 | 已确认：与结果脱钩 |
| F3 | tests/test.py:90-96 | `_cancel` 吞 BaseException | cancel 异常不可见 | 已确认：吞异常 |

规则：
- `test.sh` 的每一行**奖励写入 / 退出码 / 路径 / cd** 都要有一行结论；这几乎是命中率最高的地方。
- `test.py` 里的 helper 按函数过：吞异常、吞输出、改时序、超时缺失，各算一类。
- 这一本账不能空；空着说明只看断言、没看验证入口。

## 账本 B：三向追溯

文件：`work/ledger-trace.md`

> 这张表是**唯一**的 R 覆盖表：P3 填「覆盖测试」，P5 填「覆盖 rubric」。P5 不另开第二张表。
> 表里的 `T10/R06` 是占位示意，不是模式库编号。

| R | 题面要求（可观察） | 覆盖测试 | 覆盖 rubric | 判定 |
|---|---|---|---|---|
| R2 | 取消 pending：协程体一步不执行 | test_pending_cancel（弱，只查异常） | 条目 2（弱，只查状态） | 测试缺副作用断言 → 一条；rubric 缺条目 → 一条 |
| R3 | 取消 running：停在检查点、finally 执行 | test_cancel_cleanup（只查时间） | 条目 1/2（只看状态） | 测试验错 + rubric 重复/无锚点 |
| R4 | 已完成 cancel 返回 False；二次 cancel 返回 False | 无 | 无 | 测试缺 → 一条；rubric 缺 → 一条 |

规则：
- 一行一条 R。**每条 R 必须有「覆盖测试」或明确写「无」**。
- 覆盖 rubric 写条目编号；没有就写「无」。
- 判定列写「OK / 缺 X / 弱 X」，指向候选 issue。

## 账本 C：rubric 条目

文件：`work/ledger-rubric.md`

| # | 条目 | 分值 | 判据/锚点 | 题面依据 | 参考解得分 | 可观察性 | 重复 | 结论 |
|---|---|---|---|---|---|---|---|---|
| 1 | 取消后状态为 cancelled | 20 | `state == "cancelled"` | R3 部分 | 20/20 | 可 | 与条目 2 重复 | 重复计分 |
| 2 | 取消生效 | 20 | 仍是 `state` | R3 | 20/20 | 可 | 与条目 1 重复 | 重复计分 |
| 4 | 必须用 TaskGroup | 15 | 代码里有 `TaskGroup` | 题面无 | 0/15 | 可 | 无 | 矛盾/惩罚正确 |

规则：
- 一行一条 rubric 条目，包括「满分/档位」说明行。
- 「参考解得分」必须真的逐条打，不许估。
- 「可观察性」写标注员实际能看到什么（diff / 测试输出 / 运行行为）；看不到就标「不可」。
- 最后单独一行做算术：`Σ 分值 = ?`，对照声称满分。

## 每个测试函数的三问

1. **空实现会挂吗？** 把被测函数换成 `pass` 或占位返回，这条断言还过吗？过 → `wrong_validation`。
2. **只做断言里那件事的实现会过吗？** 例如断言只查 `state`，就写一个「只改 state、不打断执行」的实现。
3. **题面这条要求，哪一行断言会让违反它的实现失败？** 指不出来 → `missing_validation`。

第 3 问的答案要写成一句可执行的话，例如：
> R2「取消 pending 时协程体一步不执行」：`test_pending_cancel` 应在 await 后断言 `data["steps"] == 0`；现在没有。

## 候选池

文件：`work/candidates.md`

先求全，后求准。每条候选只写一行：

```
C07 | tests/test_outputs.py:52 | 疑似 T04 | cleanup 测试只查 elapsed，不查 cleanup 标志 | 待变异验证
C08 | rubric.md:24 | 疑似 R02 | 条目 1 与条目 2 都看 state | 待并排
```

规则：
- 候选阶段不写完整五项，不纠结类型；先记位置和一句话。
- 每条候选标「证据等级」：静态 / 变异 / 参考解仿真 / 双标注员。
- 成稿时只把「已确认」的转成 issue；「可疑」留在候选池，不硬写。

## 归并规则

**合并键**：`文件 + 函数（或 rubric 条目）+ 机理`。

**可复现的合并判据**（机理说不清时用这个）：看两条的 `suggestion` 改的是不是同一处——
- 同一处 + 同一修法 → 合并成一条。
- 同一处 + 不同修法（改断言 vs 改评分条目）→ 两条。
- 不同处 + 同一修法 → 合并，位置列全。
- 不同处 + 不同修法 → 两条。

合并：
- 同一个 `test.sh` 里 `|| true` 和无条件 reward 是同一个机理（奖励与结果脱钩）→ 一条。
- 同一个函数里「不查 steps」和「不查 cleanup」如果都是「只查代理信号」→ 可以合并，但要在 description 里列全两个断言；如果一个是 `false_rejection`、一个是 `wrong_validation`，不要合并。
- rubric 的「必须 TaskGroup」同时是 `contradicts_code` 和 `penalizes_correct` → 一条，主导类型 `contradicts_code`，impact 写惩罚。

不合并：
- 不同文件、不同函数、不同机理。
- **同一个位置、不同机理**：同一个 test 里「只查异常类型」与「墙钟阈值 flaky」是两条；同一个 rubric 行上「重复计分」与「缺核心条目」也可以并存。位置相同不等于问题相同。
- 一个是「测试没覆盖」，一个是「测试覆盖了但验错」——即使指向同一条 R，也是两个不同修法。

## 覆盖率的内部算法

```
测试覆盖率 = 有结论的测试函数行 / 测试函数总行
流程覆盖率 = 有结论的 flow 行 / flow 总行
要求覆盖率 = 有映射的 R 行 / R 总行
rubric 覆盖率 = 有结论的 rubric 条目行 / 条目总行
```

四个都到 100% 才允许进 P6。注意：这是**过程覆盖率**，不是对 hidden gold 的召回；它只能保证「没有漏看」，不能保证「都看对了」。

## 时间不够时的取舍

1. 先把四张账本填到 100%（哪怕结论全是「可疑」）。
2. 再把「已确认」的候选写成完整五项。
3. 最后才做变异探针和双标注员。
4. 任何时刻 `review.json` 必须能通过 `validate_review.py --strict`。

宁可交 20 条证据完整的，不要交 40 条一半空着的。
